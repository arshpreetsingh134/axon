## 0. How this spec was produced (clean-room method)

| Source | What it gave | Tool |
|---|---|---|
| Embedded Go build info | Go 1.27.2, module graph, ldflags (`-X main.version`), CGO on, dependencies | `rea` → `inspect_go_binary` |
| `--help` for all 210 verbs | Full command, flag and argument surface | Run as a black box (all exit 0; no side effects) |
| Sandbox runs in a scratch dir | Generated file trees, stdout/stderr layout, exit codes, state files | Black box |
| Binary string table | `MYCEL_*` env vars, dotfile and state paths, embedded template names, diagnose finding IDs | `strings` plus a byte scan |
| **Go symbol table (`__gopclntab`)** | 50,133 function names (12,490 in Cogniworks packages), giving the internal package architecture (§1.2) | Go's stdlib `debug/gosym` (a ~30-line parser that never runs `mycel`) |
| **Ghidra 12.1.4 decompilation** (pass 2) | Exact algorithms: verb suggestion, port allocation, run lock, release digest, workload env injection (§2.2, §3.6, §3.8, §4.1, §4.5) | `rea` MCP: `open_binary` (provider `ghidra`), `binary_overview`, `set_addresses_names`, `procedure_pseudo_code` / `batch_decompile`, `read_bytes` |
| Real repos in this workspace | Real-world mycelfile, env, release and journey formats | File reads |
| An architecture document in a product repository | Concepts and runtime topology | Reading |

**Ghidra caveat:** Ghidra 12.1.4 rejects Go 1.27 ("Untested Go version"), so its own Go analyzers
recovered **no** symbol names (51,321 anonymous procedures). Names were recovered from the binary's
own `pclntab` with Go's standard library and loaded into the REA/Ghidra session with
`set_addresses_names`. Only then were the targeted functions decompiled.

**Licensing:** `mycel` ships under **Apache-2.0** (`LICENSE` and `NOTICE` sit next to the binary), so
analyzing it, decompilation included, is permitted. Its NOTICE reserves the *trade names*
"mycel" and "mycel_*", so the new tool and its artifacts must not use them as branding (§9 Q2).

**What decompilation was (and wasn't) used for:** pass 2 looked at Ghidra pseudocode for **9
functions** (§Appendix B) to answer specific behavioral questions. The answers are written below as
**behavior** (inputs, outputs, ordering, constants), never as code. No pseudocode, control-flow
shape, or identifier naming from mycel appears in this document or may appear in axon.

Clean-room rules for Phase 2:
1. Implementation works from **this document only**. It never uses mycel's help text dumps,
   generated files, symbol lists, or decompiler output (all kept in the scratchpad, Appendix A).
2. Every template (mycelfile, compose, routes, SQL, Dockerfiles, READMEs, Svelte/Go scaffolds) is
   **written fresh**. They are shaped by the *required keys and behaviors* below, never by copying
   mycel's comment text.
3. Help strings are written in our own words. Only command names, flag names and semantics match.


### 0.1 Naming (rev 3)

axon uses its own names everywhere. It reads mycel's names in **compat mode**, which is
detected automatically (`--compat auto|mycel|off`, `AXON_COMPAT`). "mycel" remains in this
document only where it names one of these:
- the reference tool that was analyzed;
- the compat-mode layout axon also reads;
- the **runtime contract** of the closed core and module images. Those images read the
  `MYCEL_*` workload variables (§3.8), the `/app/mycelfile` path and the `mycel_iam` token,
  so axon must keep generating those names.

| Concept | axon (native) | mycel (read in compat mode) |
|---|---|---|
| descriptor | `axonfile` | `mycelfile` |
| cluster infra dir | `.axon.infra/` | `.mycel.infra/` |
| state dir (run-state, lock, spool, build cache, per-app stacks) | `.axon.infra/.axon/` | `.mycel.infra/.mycel/` |
| controller dir | `<name>.axon/` | `<name>.mycel/` |
| user config / port registry | `~/.config/axon/` (`ports.toml`) | `~/.config/mycel/` (read too, so ports never collide) |
| CLI env vars | `AXON_*` | `MYCEL_*` accepted as fallbacks |
| generated-file header | `GENERATED by axon` | — |
| Kubernetes object prefix | `axon-` (`axon-app-env`, …) | `mycel-` kept on compat clusters so live namespaces update in place |
| axon-only settings beside a mycelfile | `<infra>/axon.toml` (overlay) | — |
| workload env vars (runtime contract) | `MYCEL_*`, unchanged | `MYCEL_*` |

In the rest of this document, the paths in §3 (`.mycel.infra/…`) describe the layout
observed in mycel. axon's native equivalent is the axon column above.

## 1. What the tool is

A single-binary **DevOps orchestrator** for a "cluster" of web apps. From one declarative
TOML descriptor (`mycelfile`) it:

- **scaffolds** clusters, apps, modules (Go/Rust gRPC server + Svelte UI custom element), and
  workers;
- **generates** shared infrastructure ("fabric") config: docker-compose, Traefik routes,
  Postgres init SQL, Tempo/Grafana provisioning, Kubernetes manifests, and Keycloak scripts;
- **builds** app/module images and **deploys** them to Docker Compose or local Kubernetes;
- **validates and diagnoses** the descriptor, the toolchain and a running cluster;
- **tests** a running cluster with declarative HTTP "journeys";
- manages **environments** (dev/qa/uat/prod) and immutable **releases**.

In `mycel` 0.3.152 the same binary also embeds several **separate products**. Each would be a
project of its own (§8): `carto` (a code-intelligence daemon), `eos` (an LLM requirements compiler),
`harness`, MCP/HTTP servers, GitHub org administration, and AWS/Azure OpenTofu provisioning.

### 1.1 Domain model

| Concept | Definition |
|---|---|
| **workspace** | Directory holding the cluster controller dir and every member-app dir as **siblings**. Member `[[app]].name` resolves to `<workspace>/<name>/`. |
| **cluster** | The controller dir `<x>.mycel/`. Its descriptor is `.mycel.infra/mycelfile` with `build_type = "cluster"`. |
| **app (cored)** | `kind = "module"` (default) or `"iam"`. A core host plus 1..n module servers, one Postgres logical DB, routed at `<host>.<domain>`. |
| **app (project)** | `kind = "project"`. A headless worker, typically Temporal. Built from its own Dockerfile, or runs a prebuilt `image` as-is. No route unless `external_url` is set. |
| **module** | `build_type = "module"`. A gRPC server plus a UI bundle. Token = PG schema = `/m/<token>/*` route prefix = `<token>-app` custom element. |
| **fabric** | Shared infrastructure: postgres (required), plus optional temporal, keycloak, traefik, tracing (tempo + grafana) and clickhouse. |
| **product** | `[product.<name>]` (`clc`, `helix`). A vendor-licensed image installed under a member app. |
| **environment** | `environments/<env>.toml`: name, tier, namespace, release, kube context, storage, gates. |
| **release** | `releases/<version>.toml`: an immutable set of image digests plus source commits. |
| **core_image** | Optional base image that every cored app is built `FROM` (instead of compiling the core). |

## 2. CLI surface & UX contract

### 2.1 Grammar

```
axon <verb words…> [positional…] [--flag[=| ]value | --bool-flag]…
```

- Verbs are **1–3 words** (`version`, `env deploy`, `iam service key add`), resolved by
  longest match against a registry.
- Flags use **double-dash only** and may sit **before, between, or after** positionals.
  Both `--flag value` and `--flag=value` work. A boolean flag takes no value.
- **Repeatable flags** append (`--zone`, `--az`, `--case`, `--label`, `--set`, `--team`,
  `--applier-arn`, `--public-cidr`).
- Commas inside a value are kept for the verb to parse (e.g. `--env K=V,K2=V2`, `--concern a,b`).
- `key=value` positionals are used by `env set`, `cluster set` and `app set`. A **bare key**
  prints the current value.

### 2.2 Global behaviors

| Input | Behavior | Exit |
|---|---|---|
| `axon`, `axon help`, `-h`, `--help` | Root help: "common commands", then "moved", then the **full verb reference** (one line per verb with synopsis and summary, wrapped to about 100 columns) | 0 |
| `axon <verb> --help` | Usage line, blank, one-paragraph summary, blank, `flags:` table (name column aligned; descriptions wrapped and indented) | 0 |
| `axon --version` / `axon version` | `axon X.Y.Z — built from <12-char sha> at <RFC3339 UTC>` on stdout. Runs before any config loads. | 0 |
| unknown verb | `axon: unknown verb "<all remaining args joined by spaces>"`, plus ` (did you mean "<v>"?)` per the suggestion rule below. Example: `release create --help` → `unknown verb "release create --help" (did you mean "release list"?)` | **2** |
| unknown flag | `axon: <verb>: unrecognized flag --x` | **2** |
| missing required positional | `axon: <verb>: missing required argument(s): <names>` | **2** |
| verb needs a context dir that is absent (no mycelfile found) | `axon: no mycelfile in . — \`<verb>\` runs in an app directory` | **3** |
| runtime failure | `axon: <message>` (wrapped errors keep their chain) | **1** |
| `--check` mode with pending changes (`cluster generate --check`, `carto drift --check`, …) | lists the changes | **1** |
| validation with blocking problems (`env check`) | per-problem `✗` lines with `repair:` hints | **1** |

**Verb suggestion rule** (confirmed by decompilation and by probes): there is **no edit distance**.
Take the typed **first word**. Among all registered verbs, and then all alias names, keep those
that **start with** it. Suggest the **shortest**; ties go to the first in sorted order. No match
means no suggestion. Examples: `cluster` / `cluster bogus` → `cluster new` (`cluster new` and
`cluster set` are both 11 chars; `new` sorts first); `release create` → `release list`;
`bogus` / `doctor` → none.

**Stream discipline (important for scripting):**
- **stdout** carries *results*: tables, JSON, explain docs, `up to date`, `next:` hints for
  `app new`, and values printed by bare-key `set`.
- **stderr** carries *progress and diagnostics*: `  generated …`, `✓ …`, `! warn: …`,
  deprecation notices, errors.
- `--json` (where offered) prints one pretty JSON document (2-space indent) on stdout.

**Moved (deprecated) verbs** still run, after printing
`axon: "<old>" is now "<new>"; the old name will be removed in a later release` to stderr:
`up` → `app run` (in an app dir) or `env deploy <env>` (in a cluster); `down` → `env undeploy`;
`platform {apply,destroy,init,outputs,plan,status,upgrade}` → `env {apply,destroy,new,show,plan,list,set}`.

**Status glyphs:** `✓` success, `✗` blocking problem, `!` warning, `·` note. Two-space indent
for sub-steps. Color only when stderr is a TTY. Honor `NO_COLOR`.

### 2.3 Completion
`axon completion bash|zsh|fish` prints a script **generated from the live verb registry**
(hidden verbs excluded): the top-level verb words, plus the sorted union of all flags.

## 3. Configuration, files & environment

### 3.1 Descriptor discovery
- A cluster verb takes `[dir]` or `--dir` (default `.`). The descriptor is at
  `<dir>/.mycel.infra/mycelfile`, falling back to `<dir>/mycelfile`.
- An app or module verb searches `./.infra/`, `./`, `./module/` (message text:
  `looked in ./.infra/, ./, and ./module/; pass -f <path>`).
- `env *` verbs run from the cluster controller dir (`--dir` overrides).

### 3.2 `mycelfile` (TOML) — schema by `build_type`

**`build_type = "cluster"`**
```toml
build_type = "cluster"
name       = "<cluster>"            # compose project prefix; also the k8s namespace stem
network    = "<cluster>-net"        # docker network
domain     = "localhost"            # apps route at <host>.<domain>; cookie Domain
core_image = "<ref>"                # optional

[fabric.postgres]   image, port                                   # required
[fabric.temporal]   image, shards (IMMUTABLE), port, ui_port      # optional
[fabric.keycloak]   image, realm, client, secret, admin_email     # optional
[fabric.traefik]    http                                          # front-door host port
[fabric.tracing]    tempo_image, grafana_image, grafana_port,
                    tempo_volume, grafana_volume                  # optional
[fabric.clickhouse] image, http_port, database, volume            # optional (cluster add fabric)
[fabric.kpi]        backend                                       # optional, default "kpi:7373"
[fabric.iam]        issuer, audience, backend, signing_key        # identity contract
[fabric.console]    push_actor, push_password, license            # change-ledger push (§5.6)
[product.<name>]    image, host, app, kb, mode                    # clc | helix

[[app]]
name = "<dir name>"     kind = "module|iam|project"   host = "<label>"   db = "<logical db>"
port = 8090             temporal = "temporal:7233"    image = "<ref>"    command = "…"
mount = "<rel dir>"     external_url = "http://…"
[app.env]               KEY = "value" | "${SECRET}"   # ${VAR} resolved from .mycel.infra/.env
```
Volume inline table: `{ name, kind = "scratch"|"durable", mount }`.

**`build_type = "app"`**: `[app] name, title, search_placeholder`; `[home] title, body`;
`[[compose]] source = "modules/<token>/module"` and optional `image, token, db (bool)`;
optional `[shell] source` (path to the core host source).

**`build_type = "module"`**: `[module] token, language (go|rust), element, ui_entry, label, backend`
(default backend `unix:///tmp/mycel_app_core/<token>.sock`).

**`build_type = "project"`**: `[app] name, title`; `[project] dockerfile`;
`[[project.build]] name, command` (**at least one required**); `[project.run] command`.

**Validation rules observed:**
- Changing `build_type` revalidates the file and **reverts on failure**, e.g.
  `build_type=project requires at least one [[project.build]] step` or
  `[module].token is required (build_type=module)`.
- A module token must be a valid DNS label when it doubles as a service name (no `_`
  in `[fabric.kpi].backend` host).
- `[fabric.temporal]` must be present if any project app declares `temporal`.
- `cluster add app --from` is required unless `--from-image` is given.
- `--kind` override: only `iam` is valid for a `build_type=module` source.

### 3.4 `environments/<env>.toml`
```toml
name = "dev"            tier = "dev|qa|uat|prod"   namespace = "<cluster>-<env>"
release = "local"       # dev starts at "local"; other tiers need a recorded release
context = "<kubectl ctx>"  domain = "…"  tls = true  ingress_class = "traefik"  http_port = 443
postgres = "in-cluster|docker"
promotes_from = "<env>"   [gates] <level> = "required"   exclude_apps = […]   extensions = […]
[storage.durable] backend = "pvc", size = "20Gi", reclaim = "retain"
# account_id = …   ← tenancy: axon ignores it (with a warning)
```
`env set` keys: `domain, release, nodes=N[,max=M], ha, nat, kubernetes, network-policy,
access=CIDR[,…], github, exclude-apps, extensions, app.<app>.<KEY>=v, gate.<level>=required,
promotes-from`. `env unset` keys: `app.<app>.<KEY>, gate.<level>, promotes-from, governance`.
Release and env names must be "safe" (`[a-z0-9][a-z0-9.-]*`); otherwise:
`environment release assignment requires safe environment and version names`.

### 3.5 Journey files (`journeys/*.toml`)
```toml
[journey] name = "…"  app = "<host>"  actor = "<email>"  password = "…"
[[step]]  name = "…"  method = "GET"  path = "/healthz"
          expect = { status = 200, json = { modules = [ { health = "SERVING" } ] } }
```
JSON expectations are a **subset match**: objects match by key, and arrays match if *some*
element satisfies the pattern. Default expectation: 2xx.

### 3.6 Release record (`releases/<v>.toml`)
`schema_version, version, created, by, commit, digest, source_lock_digest, tool_version,
platforms[]`, plus the tables `[modules] [fabric] [cores] [sources] [products] [knowledge_base]`,
each mapping a name to an image `ref@sha256:…` or a commit SHA.

**Digest (confirmed by decompilation):** `digest = "sha256:" + lowercase-hex(SHA-256(body))`.
`body` is the record **without `digest`**, serialized as TOML with a 2-space table indent in a
deterministic key order. Records with `schema_version` 0 or missing use a separate legacy body
encoding. `release check` recomputes and compares.
*Not verified:* mycel's exact key order and quoting. So axon's digests are self-consistent but
will **not** byte-match mycel-produced records unless the encoding is reverse-matched against real
`releases/*.toml` files. That's possible with the records in a real cluster repository
(see Q10). Either way, axon pins its encoder output with golden tests, because any encoder change
alters digests.

## 4. Core workflows & data transformations

### 4.1 `cluster new <dir> [--name] [--core-image]`
1. `name` = `--name`, or derived from `<dir>`. Create the workspace `<dir>/` containing
   `<dir>.mycel/` (controller) and the clc product app dir.
2. **Allocate free host ports** (algorithm confirmed by decompilation):
   1. Take an exclusive lock on `ports.toml.lock`, then load `ports.toml`.
   2. `reserved` = every port listed for **other** clusters.
   3. If this cluster already has an entry, **reuse** each of its ports that is > 0. Re-running
      is idempotent and never reshuffles ports.
   4. Otherwise, for each service in this fixed order with its start port:
      **postgres 5545 · traefik 8090 · temporal 7233 · temporal-ui 8233 · grafana 3000 ·
      clickhouse 8123**. Scan `start … start+399` (stopping below 65535). Skip `reserved`
      ports. Pick the first port that **binds on both `127.0.0.1` and `0.0.0.0`** (bind, then
      close immediately). Add it to `reserved` so later services can't take it.
   5. If a range is exhausted, collect `"<service> (searched <start>–<start+400>)"`. After the
      loop, fail with all of those listed and write nothing.
   6. Rewrite the registry only if this cluster's entry changed. Release the lock.
   The allocated ports go into the descriptor (`[fabric.postgres].port`, `[fabric.traefik].http`,
   `[fabric.temporal].port`/`ui_port`, `[fabric.tracing].grafana_port`, and the commented-out
   clickhouse `http_port`), and the summary line is printed:
   `allocated free host ports — postgres P · traefik T · temporal A/B · grafana G · clickhouse C`.
3. Write the descriptor (fabric postgres/temporal/keycloak/traefik/tracing/iam,
   `[product.clc]`, zero apps), `environments/dev.toml`, `.mycel.tf/layout`, `RUNBOOK.md`,
   `.gitignore`, scripts, and `secrets/.gitkeep`.
4. Generate an **ES256 P-256 signing key** (PKCS#8 PEM, 0600).
5. Run `cluster generate`.
6. Print a summary (`✓ cluster "<name>" scaffolded → <path> (N files + signing key)`) and
   `next:` command hints.

### 4.2 `cluster generate [dir] [--check] [--migrate]`
A pure function, **descriptor (+ member mycelfiles + env) → file set**:
- `routes.yml`: one Traefik router and service per cored app (`Host(\`<host>.<domain>\`)` →
  `http://<host>-core:9080`), plus keycloak (`:8080`) and grafana (`:3000`) when declared.
- `01-databases.sql`: an idempotent `SELECT 'CREATE DATABASE x' WHERE NOT EXISTS … \gexec`
  per distinct `[[app]].db`, plus `keycloak` and the temporal stores.
- `docker-compose.yml`: the network; services postgres, temporal(+its pg, ui), keycloak,
  tempo, grafana, traefik and clickhouse (only those declared); named volumes.
- k8s manifests: Namespace, Deployments, Services, Ingress (Traefik class), a Secret for the
  signing key, a Job to ensure databases, and RBAC.
- Header on every generated file: `GENERATED by axon from <descriptor> — do not edit by hand`.
- **Write only when the content changed.** `--check` lists the files that would change, writes
  nothing, and exits 1 if anything would change (otherwise prints `up to date`). Files the repo
  gitignores are not compared.
- `--migrate` first rewrites legacy descriptor shapes (a clc member app becomes `[product.clc]`).

### 4.3 Membership mutations
`cluster add app|ext|fabric|product`, `cluster remove …` and `app add/remove module` edit TOML
**preserving comments and ordering** (append or remove blocks textually, not a full re-serialize).
Each then re-runs generation and scaffolds `journeys/<app>_smoke.toml` when missing.
`--purge` deletes directories **after an interactive y/N confirmation**; without a TTY it refuses
unless `--confirm`/`--yes` is given (see Q4). `app remove module` without `--purge` leaves the
directory and prints how to delete it.

### 4.4 `cluster check` / `app check [--fix]` / `env check` / `env diagnose`
They produce **findings** `{id, concern, severity: blocking|risk|note, subject, cause, fix}`.
- `cluster check`: header `✓|✗ <b> blocking · <r> risk · <n> note`, then findings grouped by
  concern (`CONFORMANCE`, …). Exits 1 if any finding is blocking.
- `app check`: a **toolchain table** (`ok`/`MISSING`, version, path) for go, cargo, node, npm,
  docker, kubectl, tinygo, wasm-opt and config; then structure issues (e.g. a module dir that
  is not composed).
- `env diagnose [--json] [--concern a,b]`: concerns are `toolchain, conformance, function,
  performance, business, security, devx` (plus an undocumented `product` concern for licensed
  products). JSON shape: `{"findings":[…],"notChecked":[…]}`.

**Finding-ID catalog** (string constants recovered from the binary). axon implements the
**in-scope** ones; IDs marked ✂ belong to excluded licensing/products:

### 4.5 `env deploy <env> [release] [--build] [--target docker|k8s] [--dry-run] [--keep-on-failure] [--verbose] [--force]`
1. Take the **cluster lock** (semantics confirmed by decompilation). Create the state dir (0755)
   and read any existing lock record.
   - Held by a **live** PID that isn't ours, and no `--force` → fail with a typed "lock held"
     error naming the holder.
   - Holder PID **dead** (stale) → take over silently. `--force` → take over regardless.
   - Write a fresh record (PID, host, `startedAt` RFC 3339, plus the verb and target, mirroring
     `run-state.json`) and `run-state.json` with `completed:false`. Acquisition returns a release
     handle, which axon calls on every exit path. *Inferred, not verified:* a cross-host lock
     (another machine's PID) is treated as live.
2. Resolve the target: the flag, else wherever the cluster is observed running, else k8s.
3. `generate`; resolve `${VAR}` from `.env`; merge per-env overrides.
4. `--build` (dev only): for each app in dependency order, build the module servers (Go:
   `CGO_ENABLED=0 GOOS=linux GOARCH=<host arch>`), the UI (`npm ci && vite build`), and the
   image (thin alpine image `FROM core_image` + binaries + UI dist).
5. Bring up the fabric (`docker compose up -d` / `kubectl apply`), wait for health, run the
   DB-ensure job, provision keycloak, then bring up each app.
6. On failure: roll back unless `--keep-on-failure`. Update `run-state.json`
   (`completed:true, outcome: ok|failed`) and append to the change-ledger spool.
7. `--dry-run`: print the plan and exit 0 without changes.

`env undeploy` prints a **teardown plan** (`· remove every container of compose project X`,
`· remove network X-net`, `· keep the shared Postgres data volume`); `--volumes` asks for
confirmation. Other lifecycle verbs: `env status` (front door, verdict, containers/pods),
`env logs <env> <app> [--follow] [--tail N|all]` (default 100), and `env restart <env> <app>`
(docker only).

### 4.6 `env test <env>`
Runs the **probe gate**, then the journeys, then the trace oracles. `--journey`, `--level L0,L1`,
`--list`/`--lint` (offline), `--update-golden`, `--generate` (journey from a module's
`openapi.json`), `--derive-chaos`, `--load start|status|stop` (k6), `--chaos on|off|status`.
Writes `verify/last-run.json`: `{at, cluster, pass, probes:[{app, kind, url, report}]}`.
The probe hits `GET <url>/api/system` (core plus per-module health).

### 4.7 `app new|run|build|test`
`app new <dir> [--standalone] [--lang go|rust] [--name] [--title] [--module] [--token] [--label] [--rings test,docs|all|none]`
derives: token from dir (`.` and `-` → `_`), app name default `<token>_app`, title
title-cased, label `"<Title> (<Lang>)"`. `app run` builds, then launches the core host in the
foreground (Ctrl-C stops it). `app test` runs the pyramid: core host, shell, and each module's
`go test ./...`.

## 7. Implementation plan (for Phase 2, pending approval)

### 7.1 Language: **Go**
- Matches the domain: the tool generates and builds Go modules and Go-based Dockerfiles, and
  `text/template` + `embed` are ideal for scaffolding.
- One static binary, trivial cross-compilation (darwin/linux × arm64/amd64), and a simple
  Homebrew formula with fast startup. Rust would be equally fast but slower to build out a
  template-heavy tool.
- **Your typer/click/rich/pytest suggestions are Python.** The Go equivalents:
  - CLI: a **small custom verb registry on the stdlib**, not cobra. mycel's UX (multi-word
    verbs, interleaved flags, exact error strings, exit codes 2/3, did-you-mean, generated
    completion) is easier to match exactly with ~400 lines of our own than by bending cobra.
  - TOML: `github/BurntSushi/toml` to read, plus a **comment-preserving block editor** to write.
  - YAML: `gopkg.in/yaml.v3`. Terminal: `golang.org/x/term` (TTY detection); no TUI framework.
- **Tests:** Go unit tests (`go test`) for internals, **plus the `pytest` suite you asked for**
  as a black-box acceptance layer. It drives the compiled binary through `subprocess` and covers
  argument parsing, exit codes, stream discipline, golden-file scaffolds, `--check`
  idempotency, port-registry isolation (via a temp `XDG_CONFIG_HOME`), and TOML round-trips.
  T2 runtime tests are marked `@pytest.mark.docker` / `k8s` and skipped by default.

### 7.2 Layout
```
axon/
  cmd/axon/main.go            # wiring, version ldflags
  internal/cli/                # registry, parser, help, completion, errors/exit codes
  internal/descriptor/         # mycelfile model, load, validate, comment-preserving edit
  internal/scaffold/           # cluster/app/module/project generators + embedded templates/
  internal/generate/           # fabric compose, routes, sql, tempo/grafana, k8s
  internal/ports/              # free-port allocation + locked registry
  internal/env/                # environments/*.toml, overrides, set/unset
  internal/check/              # findings model, toolchain probe, conformance rules
  internal/runtime/            # docker/kubectl drivers, lock, run-state, spool (T2)
  internal/journey/            # journey runner + JSON subset matcher (T2)
  internal/release/            # records, digest, lock (T3)
  tests/ (pytest)  pyproject.toml  Makefile  .goreleaser.yaml
```

### 7.3 Delivery order
T1 (with tests), then T2, then T3. Each tier is a reviewable checkpoint.

### 7.4 Phase-2 deliverables you asked for
- **"Editable install":** Go has no editable mode. The equivalent is `make dev`: `go build -o
  ./bin/axon ./cmd/axon` plus a symlink into `~/.local/bin`, so every rebuild is live (or
  `go install ./cmd/axon`). The pytest harness goes in a venv via `pip install -e ".[test]"`.
- **Homebrew (free):** a public GitHub repo, a `homebrew-tap` **tap** repo, and **GoReleaser**
  in GitHub Actions. A tag push builds darwin/linux × arm64/amd64 tarballs, uploads them to a
  GitHub Release, and commits the formula to the tap. Users run `brew install <you>/axon/axon`.
  All of this is free for public repos. Step-by-step docs come in Phase 2.

## 8. Why OUT-P is recommended out of scope
Each OUT-P group is a product on its own scale: carto (multi-language tree-sitter indexing,
SQLite store, launchd daemon, MCP tools), eos (an LLM pipeline with its own document compiler),
the cloud platform (hundreds of lines of generated OpenTofu across AWS/Azure plus state
migration), and the GitHub governance suite. Reimplementing them meaningfully is several
times the size of T1–T3. They can be added later as `axon <group>` plugins without
touching the core.

### C.2 Release pipeline (observed order)

1. Stage the descriptor into an isolated per-job directory.
2. Check out each locked source at its pinned commit into a fresh sibling tree.
3. **Protected-main gate** (`release lock --check`, C.3).
4. Log in to the cloud and the registry, mirror reviewed upstream images, and set up QEMU and
   buildx from mirrored images.
5. `release create --version <v> --series <s>`: build or re-push the member images and write
   `releases/<v>.toml`.
6. Upload the record as a pipeline artifact. It reaches the default branch **only through a
   reviewed PR**, which by convention also sets `environments/<env>.toml` `release = "<v>"`.

`version` and `series` are typed by hand when the run is started. Nothing increments them.

### C.3 Protected-main gate

- For each lock entry, the tool asks the GitHub API to compare the pinned commit with the source
  repository's branch named **`main`** (the symbol is `ProtectedMain`), **not** its default branch.
  Evidence: several source repositories have `develop` as their GitHub default branch, and the gate
  passed pins that exist only on `main`. A pin that is not reachable from that branch fails with
  "source %q locked commit is not on protected main".
- **Observed defect:** when the compare body is large (1.21 MB, for a pin two commits and 142 files
  behind), the call fails with `compare source %q with protected main: invalid GitHub API response:
  unexpected EOF`. Every other source, with compare bodies of 24 KB or less, passed. The failure was
  reproducible across two runs. The exact size limit was not determined.
- Moving the pin to the branch head (an empty compare) clears it.
- **axon rule:** decide reachability with Git ancestry on a fetched mirror (`merge-base
  --is-ancestor <pin> main`; `--branch` overrides). Report "on main", "N behind main" or "not on main"; a
  pin that is behind is still accepted, matching the gate's semantics. Never depend on the size of
  a compare body.

### C.4 Deploy pipeline and check mode

`env deploy <env> <release> [--check]`:
- runs on a self-hosted runner;
- logs in with the deploy identity's cloud OIDC and builds a kubeconfig for the cluster;
- checks out the release's **recorded** sources;
- reads the cluster descriptor from the **default-branch head** of the cluster repository, not from
  the release commit. A descriptor fix merged after the release was cut takes effect without a new
  release; this was observed.

`--check`: "every apply and delete is a server-side dry-run **as the calling identity**". It is
therefore usable locally with a developer's own kube context; this is the conformance oracle for
axon's renderer (plan T1.1). It prints `check passed: N apply/delete operations validated
server-side, M steps skipped, nothing changed`. Rollout waits, Keycloak realm reconciliation and the
Temporal search-attribute job are "skipped" or "deferred".

Observed order of an official deploy:
1. licensing mode (none: licensed images start and report the license absent);
2. "official release in preprovisioned namespace %s";
3. the **required-secret gate** (C.5);
4. ensure databases (one per database-backed member);
5. remove the obsolete in-cluster postgres workload (PVC retained);
6. fabric (postgres, temporal, keycloak, tracing; ClickHouse is flagged "persistent, not backed

### C.5 Required-secret gate

Refusal text: `official release requires secret "<prefix>-app-env" in namespace "<ns>" to hold a value
for <K1>, <K2>, …; missing: <Kx>, …` (keys sorted, comma-separated).

- **Which keys are required:** every `[app.env]` value in the **cluster descriptor** that is
  *exactly* `"${NAME}"`. This was checked against two descriptor revisions, where the required set
  matched the refusal text exactly. Materialization files contributed none. The symbol table names
  the helpers `neededAppEnvSecretNames`, `resolveAppEnvSecrets` and
  `requireProvisionedAppEnvSecret` in `k8s/appenv.go`.
- In official mode the secret is **never written** by the tool; it must be provisioned
  out-of-band.
- The tool's own `env check <env>` does **not** run this gate; it reported "no problems found" for
  an environment whose deploy then failed it. axon's `env check` closes that gap.
- **Comments do not count.** The descriptor that deployed successfully contains `${VAR}` in a
  comment, and `VAR` was not in the secret. A teammate's rewording of another such comment was
  therefore unnecessary. axon ignores comments.

### C.6 Image pins and digests

- The build pipelines push `<registry>/<image>:<cluster-commit>`. The digest to pin is the **image
  index (manifest list) digest**, printed in build logs as `"containerimage.digest": "sha256:…"` and
  as `exporting manifest list sha256:…`.
- A digest must be consistent across: the materialization file (`image = …@sha256:`), the business
  smoke workflow (`image: …@sha256:`), the worker's `FROM …@sha256:`, and the build workflow's
  `revision:` for the source commit. The release record's `[modules]` digests are the re-pushed
  copies (C.1), so they are not compared byte-for-byte with the pins.
- Severity follows what the pipeline releases over (0.1.25 released with both of these): a
  disagreement among the pins a release deploys (materialization files, Dockerfiles) is blocking; one
  that only a workflow carries (the smoke test runs another build) is a risk, and so is a build
  `revision:` outside the lock (the next build is not of the locked source).

### C.7 Concurrency

cannot tell whether the run ahead of it is a check or a real deploy.

### C.10 IAM configuration and demo people

The IAM configuration ConfigMap (`<prefix>-iam-configuration`) holds three JSON files. Each is
encoded with two-space indentation, no HTML escaping, and a trailing newline.

- `applications.json`: `{schema_version: 1, realm, account, applications}`. `realm` and `account`
  are the namespace. There is one application per switcher app, sorted by application id, with keys
  in this order: `application_id`, `client_id` (the same id), `product_id` (the module token as
  declared, underscores kept), `catalog_version`, `roles`, `role_permissions` and `pages` (only
  when the catalog has them), `teams` (one role per team, in catalog order), `redirect_uris`
  (`https://<host>.<domain>/auth/callback`), and `public_jwk`.
  - A business catalog has roles `access` and `admin`, with teams `access` and `administrators`.
    Its version is `"r"` plus the first 12 hex digits of the SHA-256 of the compact roles list.
  - The platform catalogs (identity, analytics, console, workflow manager) declare their own roles
    and teams. Their versions are not reproduced yet.
  - `public_jwk` is derived from the application's proof-key secret, so a reader cannot compute it.
- `providers.json`: one OIDC provider: `admit` `any_verified`, `client_id` and the realm from
  `[fabric.<identity provider>]`, `id` `keycloak`, issuer `https://keycloak.<domain>/realms/<realm>`,
  and `name` `Keycloak (<realm>)`.
- `seed.json`: `{schema_version: 1, realm, account, people}`. There is one person per
  `[[people]]` of the cluster root's `demo_people.toml`, sorted by email, with keys `subject`,
  `issuer`, `email`, `name` and `teams`. Teams keep file order, and a team that no deployed app
  declares is dropped. The password is never written.
  - **Subject (pass 2, `DemoSubject`):** a version-5 UUID (SHA-1) in the RFC 4122 DNS namespace
    `6ba7b810-9dad-11d1-80b4-00c04fd430c8`, over the name *realm*, a zero byte, then the
    lower-cased email. This was verified against all five people of a live environment. Because
    the subject is deterministic, a person's identity survives redeploys and realm resets.

The ConfigMap's `mycel.dev/iam-configuration` annotation, which the IAM Deployment repeats, is a
16-hex-digit content hash whose input is not yet reproduced.

### C.11 The dev profile (a developer's namespace)

A pipeline-released cluster whose members are image-backed also has a `dev` environment, deployed
by `axon up` from the same pins. It renders with the official rules, with these differences
(observed against a namespace deployed by the reference tool):

- The release is `local`. Images are the members' pins and each worker's Dockerfile `FROM` pin.
  Platform images, which the repository doesn't pin, are read from the live Deployments.
- URLs use `http://<host>.<domain>:<front door port>` (the `[fabric.traefik] http` port) instead of
  `https://<host>.<domain>`.
- Postgres is the local container, reached at `host.docker.internal:<[fabric.postgres] port>` as
  the cluster's database user. The URL is `postgres://<user>:$(POSTGRES_PASSWORD)@…/<db>?sslmode=disable`,
  with `POSTGRES_PASSWORD` from the `postgres-credentials` secret.
- Deployments carry `mycel.build/image-id`, the image digest. There are no image pull secrets.
  The kubelet uses the local image store, so the deploy pulls missing images with the developer's
  own registry login.
- Ingresses use the `web` entrypoint only. Host aliases point at the `traefik` Service.
- No fabric, databases, NetworkPolicies or singletons are rendered: the local bring-up owns them.
- `environments/dev.overrides.toml` `[app_env.<app>]` values are applied last, for apps and workers.
- A member without its proof-key secret, which the reference tool's deploy creates, is left as it
  is, along with the members of its project. The IAM configuration still declares their teams, and
  the console keeps their live topology.

The deploy applies only created or changed objects (client-side apply, so the last-applied
annotation stays the plan's oracle), waits for each rolled-out Deployment, and scales to 0 an
unrendered `<name>` Deployment once its rendered `<name>-worker` is ready.

Before anything rolls out, every key the rendered workloads read from Secret `mycel-app-env` (a `secretKeyRef`
without `optional`) must exist: a pod whose key is missing never starts. A missing key is copied from the developer's
values (the secret store, then `<infra>/.env`, then the process environment; an empty value counts as set). A key
whose value there differs from the Secret's is updated, so an edit to `.env` reaches the next deploy; keys only the
Secret holds (such as generated client keys) stay as they are. Anything still missing stops the deploy, naming the keys, before any workload
changes. Values are never printed.

### C.12 Local builds in the dev profile (axon extension)

The reference tool's laptop deploy runs these clusters' pinned images; it cannot run a change before
the pipeline has built and pinned it. `up --build` closes that gap without a second build recipe:

- Recipes are derived from the cluster's own build workflows (`.github/workflows/*.yml`, except the
  generated `mycel-*` ones): for each `docker/build-push-action` step whose `tags` name a member's image
  repository, its `file`, `context`, `target` (built with `--target`), `build-contexts` and
  `build-args`, with each matrix row expanded and the expressions `matrix.<key>`, `'literal'`, `a == b`
  and `cond && 'x' || 'y'` evaluated (anything else is empty). Every `actions/checkout` path is
  replaced by the local checkout whose `origin` is that repository (searched under the workspace); the
  cluster's own checkout is the cluster directory. Watch paths are the Dockerfile's folder and what it
  copies from named contexts (`COPY --from=<context> <src>`, build args expanded). A member whose
  checkout or Dockerfile is not found locally keeps its pin (`--debug` says why).
- `[[local_build]]` in `axon.toml` (never in the descriptor) overrides the derived recipe, member by
  member. It maps members to the pipeline's
  Dockerfile, context, named contexts (`--build-context`) and build args, with per-member args. Values
  may use `{workspace}`, `{cluster}`, `{target}`, `{token}` (the member's first `[[compose]]` token),
  `{checkout}` (`[[materialization]] local_checkout_path`), `{source_path}`, `{source}` and `{commit}`
  (the checkout's HEAD). Relative paths resolve against the cluster directory.
- Selection: `--app` names members (built regardless of drift); `--rebuild` takes every member a
  recipe covers and passes `--no-cache`. Otherwise a member is built when `git diff <pin> HEAD --
  <source path>` is not empty and HEAD holds the pin's work (the source lock's commit for its
  `source_member` is an ancestor of HEAD, or every commit the pin has and HEAD lacks is a merge, as
  when the pin is main's merge of develop: `git rev-list --no-merges HEAD..<pin> -- <source path>` is
  empty), or when `git status` shows changes under its source path or a `watch` directory.
  An empty diff means the checkout is at its pin whatever its history. A checkout whose content differs
  but is behind or beside its pin, or without the pin's commit, keeps the pin and is reported. A member no recipe covers keeps its pin.
- A member whose build fails keeps its pin and is reported; the deploy goes on.
- Each image is built natively with `docker build` and tagged `local/<k8s name>:<12 hex of its image
  ID>`. The render replaces only those members' images; pull policy stays `IfNotPresent`, so the
  kubelet uses the local store. A rebuild that changes nothing keeps its tag and rolls nothing.
- `--app` limits the rollout as well: every member not named keeps the local build its Deployment runs
  (`local/<k8s name>:<id>`) instead of going back to its pin.
- `--dry-run` reports what would be built and renders with the pins.

### C.13 Workflow client identity in the dev profile (axon extension)

Under app core 0.2 a workflow worker calls apps as a service principal (`private_key_jwt`). A project
member declares one through its environment (descriptor `[app.env]` with the environment's
overrides): `WFC_SERVICE_CLIENT_ID` (principal), `WFC_SERVICE_KEY_FILE` (where it reads its key),
`WFC_SERVICE_AUDIENCES` (JSON, origin → application ID: the sites it calls), optionally
`WFC_IAM_ISSUER` and `WFC_SERVICE_CLIENT_PER_AUDIENCE`. In the dev profile the deploy:

1. Keeps a Secret `<k8s name>-service-key` per member: data key `key.pem`, and with
   `WFC_SERVICE_CLIENT_PER_AUDIENCE=1` one `<suffix>.pem` per site (`<suffix>` = the site's last
   dot-separated segment). Missing keys are new P-256 keys; existing ones are kept.
2. Mounts it read-only into the rendered worker at the key file's folder (`key.pem` under the key
   file's name, the others under their own; mode 0440, pod `fsGroup` 65532).
3. Renders the IAM catalogs from each member image's `io.mycel.module.access` label (strict JSON;
   catalog version `"r"` + sha256 of the compact roles JSON, first 12 hex), and restarts the IAM when
   its configuration ConfigMap is applied.
4. Signs in to the cluster IAM's admin API as `[fabric.console] push_actor` and, idempotently, per
   principal: creates the service account (owner: that actor) or makes the environment's key its only
   key (add, then revoke the others); grants, on each of its sites, the catalog roles that carry
   `workflow.call`; then asks the token endpoint for a token per site. Principals are `<client>` on
   every site, or with `WFC_SERVICE_CLIENT_PER_AUDIENCE=1` `<client>--<suffix>` on its site only.

Observed in Mycel IAM 0.2.0-rc.28, and why the per-site form exists: a service principal granted on
more than one site gets tokens, but the target host's session check refuses them
(`session_ended_by_iam`); IDs are letters, digits, `.`, `_`, `-`, at most 64 characters; a public
key once registered on one principal is refused (`invalid_client`) on another, even after revocation.

### C.14 Service clients in the dev profile (axon extension)

Besides the per-site workflow principals of C.13, members may declare single-site service clients, each a principal
with its own key that calls exactly one application. The dev deploy finds them in each member's environment (with
the environment's overrides) and provisions them the same way:

- **A workflow client's identity map:** `WFC_SERVICE_IDENTITIES` (JSON, origin → env prefix, ignored when
  `WFC_SERVICE_CLIENT_PER_AUDIENCE=1`) with `WFC_SERVICE_AUDIENCES` (origin → application): principal
  `<prefix>CLIENT_ID`, key `<prefix>KEY_PEM_BASE64`. The C.13 default principal then covers only the origins the map
  does not; none, when it maps them all.
- **An app-to-app client:** `<T>_CLIENT_ID` with `<T>_CLIENT_AUDIENCE` (the application it calls) and
  `<T>_CLIENT_KEY_PEM_BASE64`.
- **A client with an audience map** (the Forms shapes): `<P>_CLIENT_ID` and `<P>_KEY_PEM_BASE64`, where either
  `<P>_AUDIENCES` is an origin → application map with exactly one entry (that application), or `<P>` is `<Q>_<T>` and
  `<Q>_AUDIENCES` is such a map shared by several clients. In the second case the application is the map's entry for
  the origin in a `*_<T>_URL` setting of the same member, else the one entry whose application's last dotted segment
  is `<t>`. Anything ambiguous is not a client.

Only keys given as an app-env Secret reference (`${NAME}`) are managed: before the render, every such `NAME` missing
or empty in Secret `mycel-app-env` gets a new P-256 key, stored as the base64 of its PEM (a later `kubectl apply` of
that Secret keeps keys it did not apply). A client whose ID or audience is still a reference, or whose key is inline
or a file, is reported and left alone; a principal declared for two sites or keys keeps its first declaration.

After the rollout each client is registered (owner: `[fabric.console] push_actor`), made to hold exactly that key,
and granted on its site, then checked with a token request. The roles: the overlay's `[service_roles]` entry for the
principal (`"<principal>" = ["<role>", …]`); else the catalog role named like the principal; else the catalog's only
role with permissions besides `access` and `admin`; else, for an identity-map entry, the roles that carry
`workflow.call`. Otherwise the client is reported and not granted. IAM's grant sets a principal's role list on a
site, so when any role is missing the grant sends every role the principal should hold there.

### C.15 Forms Policy grants in the dev profile (axon extension)

Forms checks its own grants (`/m/forms_policy/grants` of the Forms Policy app) besides IAM roles. The overlay's
`[forms_policy]` names the app, the tenant and, per service principal, its grants as
`"<resource_type>:<resource_id>:<action>"`:

```toml
[forms_policy]
app    = "acme.all.all.forms.forms-policy"
tenant = "demo-preview"
[forms_policy.grants]
"forms-worker-registry" = ["ecm_archive:*:read", "ecm_archive:*:archive"]
```

After the service clients (C.14), the deploy signs in as `[fabric.console] push_actor`, lists the tenant's grants
through the app's front door, and adds the missing ones for subject `service:<principal>`. The actor must hold
`policy_grant` admin in the tenant. A refusal is reported with what to do and does not fail the deploy.
